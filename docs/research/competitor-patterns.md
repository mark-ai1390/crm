# 4sales CRM: конкурентные паттерны для редизайна

Дата проверки источников: 12 октября 2026, Asia/Dushanbe.

## Границы исследования

Изучена официальная документация retailCRM, Attio, Pipedrive, Twenty, Linear и Shopify. Это кабинетное исследование возможностей продуктов, не тестирование с пользователями и не доказательство роста бизнес-показателей. Указанные функции подтверждены источниками; предложения для 4sales ниже являются нашими проектными гипотезами. Тарифы и количественные лимиты не сравнивались.

Linear рассматривается как ориентир организации работы, Shopify - как источник паттернов обработки заказов и остатков. Их предметную модель не следует целиком переносить в CRM.

## Доменная модель: решения, влияющие на прототип

### 1. Связанные записи и исторические снимки

В retailCRM данные существующего клиента можно подставить в заказ, однако изменения контактов и адреса в конкретном заказе сохраняются для него. Изменение карточки клиента не переписывает предыдущие заказы. [S15]

**Решение для 4sales:** заказ хранит customerId и собственный снимок покупателя/доставки. Позиция заказа хранит productId/variantId, количество и зафиксированную цену. В карточке товара можно изменить текущую цену, но уже подтверждённый заказ не должен молча пересчитываться. Последнее правило - наша гипотеза реализации, а не цитата о retailCRM.

Минимальные связи:

- Клиент → заказы, задачи, обращения, история.
- Заказ → клиент, ответственный менеджер, позиции, платежи, доставка, задачи, события.
- Позиция заказа → вариант товара, склад/резерв, количество, цена, скидка.
- Товар → варианты/SKU, остатки по складам, движения, связанные заказы.
- Коммуникация → клиент и необязательный заказ; автор, канал, время, состояние.
- Задача → исполнитель, срок, статус и связанные записи.
- Событие → сущность, автор, время, предыдущие/новые значения.

### 2. Проверяемая история

retailCRM показывает изменения статуса с автором и временем нахождения в нём; общая история содержит старое и новое значение, а источник изменения может быть менеджером, триггером или интеграцией. [S16]

**Решение:** единая лента с фильтрами «Все / Изменения / Сообщения / Задачи». Лента не должна стирать историю при редактировании записи. В демо автоматическое изменение отмечается как действие правила.

### 3. Остаток - результат операций

По модели Shopify физическое наличие = доступно + зарезервировано + недоступно; ожидаемое поступление не считается доступным до приёмки. [S14]

**Решение:** создание/отмена резерва и отгрузка должны менять остатки предсказуемо. Для демо достаточно простых, явно описанных операций и запрета отрицательного доступного остатка. Полноценную складскую ERP изображать не требуется.

## Автоматизация: небольшой объём, понятное поведение

Официальные источники подтверждают три связанных паттерна:

1. retailCRM: событие запускает проверку условий и действия; есть пример автоматической задачи после пропущенного звонка по существующему заказу. [S17, S18]
2. Attio: журнал выполнения показывает шаги, входные/выходные данные, результат и ошибку; повторный запуск учитывается как новая попытка. Документация отдельно описывает риск зацикливания правил. [S19]
3. Twenty: сценарий включает триггер, последовательность шагов и переменные; доступны события записей, ручной запуск и расписание. [S20]

**Предлагаемый объём 4sales:** список правил, простой редактор «Когда / Если / Сделать», включение, пробный запуск и журнал. Начальные правила:

- Новый заказ без ответственного → назначить менеджера по выбранному правилу.
- Заказ ожидает подтверждения дольше установленного срока → создать задачу.
- Заказ подтверждён и оплачен → добавить в очередь подготовки к отправке.
- Доступный остаток ниже порога → уведомить ответственного по товару.

В веб-прототипе запуск моделируется локально. Он не должен выдавать симуляцию за реальное SMS, платёж, письмо, фоновый сервер или внешнюю AI-интеграцию. Один запуск не создаёт повторно одну и ту же задачу при повторном рендере.

## Аналитика, связанная с работой

Pipedrive разделяет фильтры отчёта, график и таблицу исходных записей. Отчёты могут использовать поля связанных сущностей, при этом измеряемая сущность остаётся явной. [S21, S22] Twenty задаёт для виджета источник, агрегацию, группировку и фильтры. [S23] В retailCRM есть отчёт по времени нахождения заказа в статусе, причём рабочее время и назначение менеджера учитываются определённым образом. [S24]

**Решение для 4sales:**

| Показатель | Что должно быть определено | Следующее действие |
|---|---|---|
| Оплачено за период | Сумма подтверждённых платежей минус возвраты; дата платежа | Открыть платежи/заказы, вошедшие в расчёт |
| Новые заказы | Заказы по дате создания; исключения перечислены | Открыть отфильтрованный список |
| Требуют внимания | Правила включения и причина у каждой строки | Выполнить задачу, назначить или отложить |
| Заказы без движения | Порог и дата последнего значимого события | Открыть очередь и назначить следующий шаг |
| Продажи по каналам | Одинаковый период, валюта и определение суммы | Перейти к заказам выбранного канала |
| Нагрузка менеджера | Активные заказы + просроченные задачи | Переназначить конкретные записи |
| Низкий остаток | Доступное количество относительно порога | Открыть товар и создать приход |

Это предложения. В макетах и прототипе нельзя заявлять доказанное улучшение конверсии, выручки или скорости работы без измерения. Лучше показать, что числа пересчитываются из тех же записей, которые видны пользователю.

## Гипотезы и способ проверки

| Гипотеза | Проверочный сценарий | Что измерять при будущем тесте |
|---|---|---|
| Рабочая очередь помогает начать день без поиска по разделам | Найти три самых срочных заказа и определить следующее действие | Правильность выбора, время, пропущенные причины |
| Предпросмотр сохраняет контекст обработки списка | Проверить пять заказов, изменить ответственного, вернуться в очередь | Потеря фильтра/позиции, лишние переходы, ошибки |
| Разделение оплаты и доставки делает статус понятнее | Объяснить состояние частично оплаченного, неотправленного заказа | Ошибочная трактовка статуса |
| Связанные карточки сокращают ручной поиск | По сообщению клиента найти заказ, товар и исполнителя | Успешность и число ручных поисков |
| Дашборд с переходами к данным помогает объяснить показатель | Найти, из каких заказов состоит выручка канала | Совпадение суммы и понимание периода |
| Объяснимые правила вызывают меньше неопределённости | Запустить правило, найти созданную задачу и причину срабатывания | Возможность объяснить действие и восстановить ошибку |

Никакие значения этих измерений сейчас не получены.

## Визуальное направление: наша интерпретация

Предлагается использовать выбранный пользователем ориентир Attio/Linear через дисциплину интерфейса: нейтральная поверхность, аккуратные разделители, единая плотность строк, ясные состояния, компактные контекстные действия. Документация подтверждает интерактивные паттерны, но не доказывает, что конкретная палитра или размер текста лучше для аудитории 4sales.

Сохраняем характер 4sales через логотип, тёмный компактный сайдбар и один синий акцент. Цветные поверхности предназначаем для приоритета, статуса и действия. Главный экран начинает рабочую сессию: приоритетная очередь рядом с ограниченным набором показателей. Большие декоративные градиенты, постоянно движущиеся графики и имитация AI без полезного действия не нужны.
